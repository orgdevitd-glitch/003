# Технический аудит вкладки «Реестр проектов» (Project Registry) и миграция с legacy _metrics

Данный документ содержит карту источников данных, анализ логики фильтрации/сортировки для вкладки **«Реестр проектов»** (компонент `ProjectTable.tsx`) и описывает результаты успешного перехода на единую северную методологию расчетов (`ProjectEvaluation`).

## 2. Новая архитектура расчетов и оценок

После завершения миграции вся расчетная логика и отображение данных были полностью переведены на современную централизованную модель расчетов.

### Ключевые компоненты новой архитектуры:
1. **Основной источник расчетов — `ProjectEvaluation`**:
   Все аналитические вычисления, включая статус здоровья проекта (прогресс, риски, качество данных), качество заполнения и статус ведения мониторинга рассчитываются централизованно. Сервер предоставляет массив оценок `ProjectEvaluation[]`, которые маппятся с проектами во фронтенде.

2. **Портфельная аналитика — `PortfolioEvaluation`**:
   Сводные метрики по всему портфелю проектов рассчитываются на базе индивидуальных `ProjectEvaluation` и агрегируют общие показатели здоровья портфеля.

3. **Frontend helper-слой (`projectRegistryMetrics.ts` и `projectRegistryStatus.ts`)**:
   - Функции получения метрик реестра (такие как `getRegistryMonitoringStatus`, `getRegistryMilestoneProgress`, `getRegistryKpiProgress`, `getRegistryRiskReasons` и др.) приведены к единому стандарту.
   - Они принимают объект проекта и соответствующую ему оценку `ProjectEvaluation`.
   - В случае отсутствия оценки, эти функции возвращают безопасные значения по умолчанию без обращения к какому-либо легаси-коду или расчетным полям.

4. **Чистый backend без генерации `_metrics`**:
   - Из серверной части полностью удалена генерация устаревших метрик.
   - Сервис `projectViewAdapter.ts` выполняет только базовое преобразование `NormalizedProject -> Project` для совместимости, но не обогащает объект проекта расчетными `_metrics` полями.

5. **AI-анализ на базе `ProjectEvaluation`**:
   - AI-ассистент и OpenAI/Gemini сервисы работают напрямую с результатами современной оценки `ProjectEvaluation`.

## 3. Что больше не используется (Удалённый Legacy-функционал)

Все устаревшие механизмы и типы были полностью удалены как из runtime-кода, так и из статической типизации:

1. **Поле `_metrics`**:
   - Полностью удалено из интерфейса `Project` в `src/types.ts`.
   - В runtime-коде проекта отсутствуют обращения вида `project._metrics` или `p._metrics`.

2. **Интерфейс `ProjectCalculatedMetrics`**:
   - Полностью вырезан из `src/types.ts`.
   - Не упоминается и не импортируется ни в одном runtime-файле, скрипте или тесте.

3. **Утилита `calculateProjectMetrics`**:
   - Была единственным тяжелым расчетным инструментом во фронтенде/бэкенде для заполнения `_metrics`. Полностью удалена.

4. **Функция `getSimplifiedStatus`**:
   - Удалена из `src/utils/projectCalculations.ts` как мертвый код, поскольку маппинг общего статуса теперь реализован через `ProjectEvaluation.projectHealth` и метод `getRegistryOverallStatus`.

5. **Файл `server/services/projectMetrics.ts`**:
   - Удален из файловой системы проекта за полной ненадобностью.

6. **Тестовые и скриптовые зависимости**:
   - Скрипты `scripts/control_test.ts` и `scripts/test-frontend-evaluation-utils.ts` были очищены от упоминаний устаревших типов и полей, переведены на современный формат работы с `ProjectEvaluation` или безопасными дефолтами.

## 4. Различия в режимах оценки рисков: Реестр против Карточки проекта

В архитектуру системы заложено методологическое разделение на два режима оценки рисков, работающих на разных наборах пороговых значений (thresholds):

1. **Режим реестра проектов (Registry Risk)**:
   - **Назначение**: Верхнеуровневый мониторинг портфеля для руководителей портфелей и Проектного комитета.
   - **Алгоритм**: Использует более строгие и чувствительные пороговые значения (`registry thresholds`).
   - **Цель**: Быстро подсветить малейшие зарождающиеся отклонения, чтобы менеджеры портфеля могли проактивно реагировать на риски.

2. **Режим карточки проекта (Project Card Risk)**:
   - **Назначение**: Детальный анализ отдельного проекта для руководителя проекта и ИИ-ассистента. Отображается в детальной панели проекта и выгружается в PDF-отчеты.
   - **Алгоритм**: Использует более лояльные, методологически выверенные пороговые значения (`project-card thresholds`).
   - **Цель**: Сфокусировать команду проекта на действительно критических отставаниях, не создавая ложной тревоги из-за несущественных технических задержек.

### Почему это не является ошибкой?
Разница в оценке здоровья одного и того же проекта между общим реестром и индивидуальной карточкой проекта — это **штатное поведение системы, а не ошибка**. Различные пороги чувствительности позволяют совместить жесткий упреждающий контроль на уровне всего портфеля с гибким и конструктивным подходом к оценке конкретного исполнителя в его персональной карточке.
