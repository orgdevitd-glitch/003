# Дашборд Проектной Аналитики 2.0 (React + Express)

Современная система визуализации, расчета и интеллектуального анализа портфеля проектов.

## 🚀 Архитектура проекта

Проект реализован по двухкомпонентной схеме:
1.  **Frontend (React / Vite / Tailwind CSS)**:
    *   Интерактивный дашборд с детализированными карточками проектов, графиками (`recharts`), дорожными картами и выгрузкой в PDF (`jspdf` + `html2canvas`).
    *   Интегрированный виджет Chat Assistant для прямого интерактивного обсуждения проектов в контексте собранных метрик.
2.  **Backend (Express / TypeScript / tsx)**:
    *   Архитектура Express API, проксирующая запросы к внешним интеграциям.
    *   Синхронизация данных с внешними источниками в реальном времени.

---

## 🔌 Источники данных и Хранилище

*   **Google Sheets / CSV**:
    *   Основной рабочий источник данных. Настраивается через `GOOGLE_SHEETS_CSV_URL`.
    *   Поддерживает автоматическое преобразование публичной ссылки листа `.../edit#gid=...` в прямой формат экспорта CSV.
*   **Локальное JSON Fallback-хранилище**:
    *   Все синхронизированные данные из Google Sheets сохраняются во встроенное файловое JSON-хранилище (`/data/`).
    *   В случае недоступности Google Sheets (проблемы с правами, ошибки сети, неверный URL), система автоматически переходит в отказоустойчивый режим `fallback`, используя последнюю успешную локальную копию, предотвращая поломку интерфейса и потерю данных.
*   **Импорт по REST API**:
    *   Дополнительный канал импорта внешних проектов (например, из Битрикс24) через приватный роут `POST /api/bitrix/projects/import`.

## 🤖 Интеллектуальный анализ (OpenAI Assistants)

Приложение интегрировано с **OpenAI Assistants API** (вместо устаревших модулей Gemini) в целях глубокой диагностики показателей:
*   **Анализ карточки проекта**: Формирует управленческие выводы, оценивает качество заполнения данных, сроки прохождения ПК (Проектный комитет) и показатели плановых весов задач.
*   **Чат-помощник (Chat Assistant)**: Ассистент в реальном времени отвечает на вопросы пользователя и ведет сквозной диалог с памятью контекста (thread-based).

## 🧪 Тестирование и Проверка качества (Validation & Testing)

В проекте настроена система автоматического тестирования и статического анализа кода для обеспечения стабильности расчетов рисков, вех и показателей. 

Для проверки качества кода и расчетов доступны две основные команды:

### 1. Быстрая smoke-проверка (`npm run test:smoke`)
Рекомендуется запускать ежедневно в процессе активной разработки перед фиксацией локальных изменений. Она выполняет быстрый прогон критически важных шагов:
*   **Статическая типизация (`typecheck`)**: Полная проверка типов TypeScript (`tsc --noEmit`).
*   **Тесты статуса реестра (`test:registry-status`)**: Проверка логики формирования статусов проектов и рисков в реестре.
*   **Тесты расчета унифицированных рисков (`test:unified-risk`)**: Проверка корректности взвешенного анализа рисков.
*   **Тесты модели весов вех (`test:milestone-weight-model`)**: Проверка распределения весов вех.
*   **Сборка проекта (`build`)**: Сборка frontend-части и компиляция backend-сервера.

```bash
npm run test:smoke
```

### 2. Полная проверка перед передачей версии (`npm run test:all`)
Обязательно запускается перед релизом новой версии приложения, передачей кода в общий репозиторий или деплоем на production. Она осуществляет последовательный запуск абсолютно всех юнит-тестов и проверок в проекте:
*   Все проверки из `test:smoke` (типы, расчет весов вех, риски реестра, сборка).
*   Тесты математических расчетов карточки проекта (`test:project-card-math`).
*   Тесты валидации импортируемых данных (`test:data-validation`).
*   Тесты нормализации данных проектов (`test:project-normalizer`).
*   Тесты оценки проектов (`test:project-evaluation`, `test:project-evaluation-fallback`).
*   Тесты расчета прогресса портфеля (`test:portfolio-progress`).
*   Тесты фильтрации по годам для дашборда и дорожных карт (`test:overview-year-filtering`, `test:roadmap-year-filtering`).
*   Тесты фильтров таблицы проектов (`test:project-table-filters`).
*   Тесты надежности локального хранилища (`test:storage-robustness`).
*   Тесты экспорта табличных данных (`test:project-table-export-data`).
*   Тесты дат и статусов таблицы проектов (`test:project-table-date-status`).
*   Тесты сортировки таблицы проектов (`test:project-table-sorting`).
*   Тесты интеграции со справочником KPI (`test:indicator-dictionary-source`).
*   Тесты генерации PDF-отчетов (`test:overview-pdf-report`, `test:project-card-pdf-report-data`).
*   Тесты нормализации стадий проектов (`test:stage-normalization`).


## 📊 Спецификация контракта данных Google Sheets

Для стабильного импорта, анализа и валидации проектных данных используется универсальный контракт структуры таблиц. Все проверки не привязаны к конкретным значениям из примера, а работают на основе стабильных математических законов и правил разбора ячеек.

### 1. Общие принципы и структура таблицы
*   **Основной рабочий лист**: Таблица должна содержать лист/вкладку с названием `Сводная` (или по умолчанию отдавать её при экспорте CSV).
*   **Принцип строк**: Каждая непустая строка в Сводной представляет **один уникальный проект или программу** (строка = проект/программа). Отслеживание сущности выполняется на программном уровне по колонке `ID`.

### 2. Спецификация колонок контракта
Таблица делится на две логические группы колонок: базовые свойства проекта (статические) и ежеквартальные динамические блоки (масштабируемые).

#### А. Базовые обязательные колонки:
*   **ID** (`ID`, `ID проекта` или `ИД проекта`): Уникальный ключ проекта. Обязателен к заполнению, должен быть целым числом больше нуля. Дублирование ID в таблице считается критической ошибкой.
*   **Название** (или `Название проекта`): Обязательная строка с наименованием проекта.
*   **Цели проекта** (или `Цель проекта`): Текстовые цели проекта.
*   **Образы результатов**: Текстовые результаты.
*   **Дата начала** (или `Дата начала проекта`): Дата старта проекта.
*   **Дата завершения** (или `Дата окончания проекта`): Срок сдачи проекта (не может быть раньше даты начала).
*   **Стадия** (или `Стадия проекта`): Одно из строго ограниченных значений справочника: `Планируется`, `В работе`, `На паузе` или `Завершен`.
*   **Вид** (или `Вид проекта`): Одно из значений справочника: `Проект` или `Программа`.
*   **Приоритет**: Строгий приоритет `0`, `1` или `2`.
*   **Ссылка на проект**: Если заполнена, должна быть корректным URL с протоколом (`http://` или `https://`).
*   **Руководитель проекта**, **Администратор проекта**, **Заказчики**, **Команда проекта**, **Владелец проекта**, **Департамент**, **Ответственный** (вспомогательные текстовые поля).
*   **Дата начала мониторинга**, **Регулярность мониторинга (1 раз в количество недель)**, **Дата последнего мониторинга** (поля настройки регламентных проверок).

#### Б. Ежеквартальные показатели (Шаблон):
Любое число кварталов и годов может динамически определяться по шаблону заголовков. Например, для года `{year}` и квартала `Q{quarter}` (где Q = Q1, Q2, Q3, Q4) колонки должны называться следующим образом:
1.  `Вехи {year} Q{quarter}` (список ключевых целей периода).
2.  `% выполнения Вехи {year} Q{quarter}` (процент прогресса по каждой вехе).
3.  `Вес вехи {year} Q{quarter}` (вес значимости каждой вехи).
4.  `Показатели проекта {year} Q{quarter}` (список текстовых метрик).
5.  `План Показатели проекта {year} Q{quarter}` (числовые плановые ориентиры).
6.  `Факт Показатели проекта {year} Q{quarter}` (числовые фактические результаты).

### 3. Алгоритмы расчетов и разбора ячеек
Универсальный парсер обрабатывает сырые строки по следующим строгим правилам:

*   **Стратегия определения лет**: Система сканирует все переданные заголовки CSV, извлекает года (например, `2026`) и формирует динамическую матрицу применимости. Алгоритм не имеет жестко вшитых годов во избежание устаревания.
*   **Оценка периодов**: Разделение квартала на `past` (прошедший), `current` (текущий) или `future` (будущий) рассчитывается динамически относительно переданной в запросе или системной даты оценки (`assessmentDate`).
*   **Применимость кварталов к проекту**: Квартал считается применимым к проекту, если период квартала пересекается со сроком самого проекта:
    *   Дата начала проекта $\le$ Конец квартала;
    *   Дата завершения проекта $\ge$ Начало квартала.
*   **Парсинг списков**: 
    *   Списки внутри одной ячейки (например, цели или несколько вех) строго делятся символом точка с запятой `;`.
    *   Окружающие пробелы игнорируются, пустые элементы отбрасываются.
    *   Списки, разделенные запятыми `,`, вызывают предупреждение валидатора (`warning`), сообщающее о необходимости разделения точкой с запятой.
*   **Парсинг дат**: Ожидается формат `DD.MM.YYYY`. Ошибочные структуры возвращают parse error. Пустые ячейки остаются пустыми, автоматическая подмена ("подтягивание" дат) запрещена.
*   **Парсинг процентов**:
    *   Поддерживаются значения вида `30%`, `80` или дробные величины Excel (значения меньше `1` переводятся в проценты с предупреждением, например, `0.25` преобразуется в `25%` с предупреждением).
    *   Общая сумма явно указанных весов всех вех проекта по всем кварталам его жизненного цикла не должна превышать 100%. Если сумма больше 100%, это считается критической ошибкой контроля весов. Если сумма меньше 100%, недостающий вес автоматически и равномерно распределяется на вехи без веса (или с весом 0%), что генерирует предупреждение (warning), но не критическую ошибку. Если все веса пустые, они распределяются поровну. См. раздел "Методология расчетов" для подробностей.
*   **Разделение типов пустоты**: Валидатор строго классифицирует пустоту:
    *   *Логически пустая ячейка* (например, факт в будущем квартале или дата последнего мониторинга для еще не начавшегося проекта) — не увеличивает ошибку и трактуется как норма.
    *   *Ошибочно пустая ячейка* (например, имя проекта не заполнено, или вехи указаны, но вес оставлен пустым) — трактуется как признак нарушения контракта.
    *   *Заполненная некорректная ячейка* (неправильная дата, некорректные символы в числах) — выводит критическую ошибку.

### 4. Спецификация отчета `ImportValidationReport`
В ответе endpoint `/api/projects` возвращается поле `importReport: ImportValidationReport` следующей структуры:

```typescript
interface ImportValidationReport {
  structureStatus: "ok" | "warning" | "error"; // Оценка колонок в XLS/CSV
  rowCount: number;                             // Общее число строк
  projectCount: number;                          // Уникальных ID
  errorsCount: number;                           // Суммарно ошибок уровня "error"
  warningsCount: number;                         // Суммарно предупреждений уровня "warning"
  issues: DataIssue[];                           // Полный плоский список всех инцидентов
  columnAnalysis: SheetContractAnalysis;         // Анализ соответствия колонок
  rowsWithErrors: number[];                      // Номера ошибочных строк (1-based)
  rowsWithWarnings: number[];                    // Номера строк с предупреждениями (1-based)
  detectedYears: number[];                       // Найденные года во вкладке
  assessmentDate: string;                        // Использованная дата оценки (ISO)
}

interface DataIssue {
  severity: "error" | "warning";
  rowIndex: number;                              // Номер строки в файле
  projectId: string;
  projectName: string;
  field: string;                                 // Имя колонки с ошибкой
  code: string;                                  // Системный код (например, "DUPLICATE_ID", "MILESTONES_TOTAL_WEIGHT_NOT_100")
  message: string;                               // Человекочитаемое описание
}
```

#### Типовые выявляемые ошибки:
1.  `DUPLICATE_ID`: Нахождение одной и той же числовой метки ID у нескольких проектов на разных строках таблицы.
2.  `END_DATE_BEFORE_START`: Ошибка ввода сроков (дата конца проекта предшествует дате начала).
3.  `STAGE_INVALID`/`KIND_INVALID`: Нарушение стандартных справочников стадий или видов активностей (например, вид `Мероприятия` вместо одобренных `Проект`/`Программа`).
4.  `MILESTONE_PROGRESS_COUNT_MISMATCH`: Количество вех (например, две вехи через `;`) отличается от количества значений процентов выполнения/весов.
5.  `MILESTONES_TOTAL_WEIGHT_NOT_100`: Превышение суммарного веса всех вех свыше 100% (для ситуации, когда сумма весов меньше 100%, формируется предупреждение с автораспределением остатка веса).
6.  `INDICATOR_FACT_PAST_MISSING`: Отсутствие фактических замеров по KPI в кварталах, которые находятся в прошедшем времени относительно текущей даты оценки применимо к проекту.
7.  `LIST_FORMAT_SEPARATOR_WARNING`: Обнаружение перечисления элементов списков через запятую вместо точки с запятой, угрожающее корректности деления строк.

## 📐 Методология расчетов и Бизнес-логика (Calculation Methodology)

В версии 2.0 бизнес-расчеты полностью вынесены на серверный слой (Node.js/Express) для гарантированного методологического единства карточки проекта, реестра, PDF-отчетов и ИИ-анализа. Алгоритмы не используют хардкод конкретных ID, названий проектов или дат, и реализуют универсальные правила:

### 1. Расчет весов вех (Milestone Weight Model)
Сумма весов вех по каждому проекту всегда приводится к 100% с использованием эффективной/нормализованной модели весов (`normalized/effective milestone weights`):
*   **Сумма весов равна 100%**: Если сумма явно указанных в таблице весов составляет ровно 100%, используются данные значения.
*   **Сумма весов меньше 100%**: Если сумма явно указанных весов меньше 100%, недостающий вес автоматически распределяется равномерно на вехи с неуказанным весом или весом 0% / 0. Такие веса считаются расчетными/распределенными (`allocated/calculated`). При этом система выдает предупреждение (warning) в слое валидации данных, но это не является блокирующей критической ошибкой.
*   **Все веса пустые**: Если по проекту не указано ни одного веса, веса распределяются равномерно между всеми вехами (равное распределение).
*   **Сумма весов больше 100%**: Если сумма явно указанных в таблице весов превышает 100%, это считается критической ошибкой контроля весов (`weightControlStatus === 'error'`).
    *   *Важно*: При ошибке весов прогресс проекта НЕ должен подменяться на 100%.
    *   *Важно*: При ошибке весов риск должен показывать причину ошибки, а не рассчитывать отставание по вехам (так как расчет отставания на некорректных весах не имеет методологического смысла).

### 2. Расчет прогресса вех (Milestone Progress)
*   **Общий прогресс (`totalProgressPercent`)**: Сумма вкладов всех вех за все годы мониторинга на основе эффективных (нормализованных) весов:
    $$\text{Total Progress} = \sum_{i} \frac{\text{effectiveWeight}_i \times \text{progress}_i}{100}$$
*   **Актуальный прогресс (`actualProgressPercent`)**: Отражает реальное выполнение относительно наступивших плановых отчетных периодов (прошедшие и текущий кварталы):
    $$\text{Actual Progress} = \frac{\sum_{\text{act}} (\text{effectiveWeight}_j \times \text{progress}_j / 100)}{\sum_{\text{act}} \text{effectiveWeight}_j} \times 100$$
    Будущие вехи имеют статус `future` и не занижают актуальный прогресс. Если у будущей вехи уже есть выполнение $>0\%$, оно сохраняется в общем прогрессе.

### 3. Расчет рисков по вехам и периодам (Milestone Risks)
Риск по отставанию вех использует ту же эффективную модель весов (effective milestone model), что и карточка проекта, детализация и PDF. Сырые (raw) веса для этого расчета не используются.
Правила обработки периодов:
*   **Только завершенные периоды**: Для активного проекта до плановой даты завершения при расчете рисков учитываются только завершенные отчетные периоды (прошедшие кварталы).
*   **Текущий период**: Текущий квартал не считается просроченным и не приводит к формированию риска по вехам, даже если вехи текущего квартала еще не выполнены на 100%.
*   **Будущие периоды**: Будущие кварталы никак не ухудшают риск проекта.
*   **Просроченный дедлайн**: Если проект прошел плановую дату завершения (deadline), но стадия проекта остается не закрытой (не завершенной), ожидаемое выполнение по вехам считается равным 100%. Любое невыполнение до 100% трактуется как отставание.
*   **Проект не начался**: Если плановая дата начала проекта еще не наступила относительно даты оценки, риск по отставанию вех не формируется.
*   **Отсутствие/невалидность дат**: Если у проекта отсутствуют или признаны невалидными даты начала или завершения, риск по отставанию вех не рассчитывается, а проект получает интегральный статус «Недостаточно данных» (что исключает ложноположительные риски).

### 4. Расчет заполненности данных (Data Completeness)
*   **Целевой уровень**: Целевой уровень заполненности данных задается единой константой `TARGET_COMPLETENESS_PERCENT` и составляет **90%**.
*   **Логика контроля**: Если заполненность ниже целевого уровня, причина риска проекта должна отражать факт и целевой уровень с использованием единого шаблона:
    `"Заполненность данных проекта составляет X%, что ниже целевого уровня Y%"`
*   **Исключение неприменимых полей**: Поля будущих лет и периоды, не применимые к жизненному циклу проекта (например, кварталы до даты начала или после даты окончания), не занижают заполненность данных.
*   **Методологическое единство**: Карточка проекта (включая детализацию) и алгоритм расчета рисков используют одну и ту же функцию расчета заполненности данных.

### 5. Режимы оценки рисков (Project Card vs. Registry Risks)
В системе специально реализованы два разных режима оценки рисков с различными порогами чувствительности (`thresholds`):
*   **Project Card Risk (Карточка проекта и PDF)**: Использует набор порогов `project-card thresholds`. Данный режим ориентирован на индивидуальную и детальную оценку проекта. Он обладает более умеренной чувствительностью, чтобы не перегружать команду проекта мелкими или техническими отклонениями.
*   **Registry Risk (Реестр проектов и портфельные отчеты)**: Использует набор порогов `registry thresholds`. Этот режим более чувствителен и предназначен для верхнеуровневого мониторинга портфеля. Он позволяет менеджерам портфеля проактивно выявлять даже незначительные зарождающиеся отклонения и вовремя предпринимать превентивные действия.
*   *Обратите внимание*: Различие оценочных зон в реестре и карточке проекта — это не ошибка расчета, а заложенная методологическая особенность системы (разные режимы чувствительности).

### 6. Сводные портфельные расчеты (Portfolio Evaluation)
*   **Portfolio Evaluation (`portfolioEvaluation`)**: Сводный интегральный отчет по всему портфелю проектов, группирующий проекты по их состоянию и вычисляющий средневзвешенную успеваемость портфеля по вехам, актуальным вехам, KPI и полноте контракта.
*   **Синхронизация по дате (`assessmentDate`)**: Фронтенд автоматически сохраняет выбранную дату оценки в `localStorage` и рендерит измененные расчетные показатели мгновенно при переключении периода.

## ⚙️ Административный режим отладки (Debug Mode)

В соответствии с требованиями чистоты пользовательского интерфейса, все технические и методологические сведения (отчёты о валидации импорта, предупреждения структуры данных, детальные показатели качества таблиц и формулы расчёта) скрыты от обычных пользователей.

Для администраторов системы и аналитиков предусмотрен скрытый режим отладки (**Debug Mode**), который активирует отображение следующих элементов:
1. **Диагностика источника Google Таблиц**: Показывает детальный статус парсинга и синхронизации потоков на главном экране.
2. **Панель технической диагностики импорта**: Позволяет увидеть плоский список инцидентов валидации (`ImportValidationReport`), дубликаты ID, ошибки приведения типов и нарушения структуры.
3. **Методологическая детализация в тултипе рисков**: В детальной диагностике конкретного проекта показывает расчётные показатели по вехам (всего и актуальным), весам и просрочке аудита.
4. **Справка по классификации уровня рисков**: Отображает свод правил классификации проектов по соответствующим категориям угроз напрямую под списком факторов.

### Активация Debug Mode:

*   **Через ссылку**: Добавьте к URL-адресу параметр `?debug=1` (например: `http://localhost:3000/?debug=1`).
*   **Через память браузера**: Выполните в консоли разработчика команду:
    `localStorage.setItem('debugDashboard', 'true')`
    Для деактивации флага удалите его командой `localStorage.removeItem('debugDashboard')` или перейдите по ссылке без параметров.
